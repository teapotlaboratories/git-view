# 2026-07-28 — a revoked device hung on "reconnecting…" instead of re-pairing

Found while verifying ADR-036 on an emulator, on a branch (`feature/control-socket`) that changed **zero**
`android/` files. The bridge half of revoke was correct the whole time — which is exactly why nothing
caught this.

## The bug

Revoking a *connected* device worked on the host: `gitview-bridgectl revoke` reported
`1 connection(s) closed`, and the socket really was closed. The app then sat on **"Connection lost —
reconnecting…" forever** — no notice it had been revoked, no pairing prompt, cached screens still
rendering so it looked online. Six sockets stayed open to `:8787`, retrying.

Two lines, in different languages, that had never been read together:

```
bridge  ws/liveChannel.ts:178    c.ws.close(4401, "device revoked")
app     AppViewModel.kt:415      if (t is BridgeException && t.httpStatus == 401)
app     4401                     no match anywhere under android/
```

A WebSocket authenticates **once, at connect**, so revocation can only reach a live client as that close
code. `BridgeClient.onClosed` discarded the code entirely (`close()`, no argument) and the reconnect loop
in `connect()` retried unconditionally. So the one close that must never be retried was indistinguishable
from a network blip, and the app dialled forever against a token the bridge would never accept again.

## The fix

- `ConnState.REVOKED` + a `WS_REVOKED = 4401` constant with the reasoning attached.
- `onClosing` **and** `onClosed` both record the code. Both matter: `onClosing` is where the peer's code
  arrives, and answering it with `close(1000, null)` is what makes `onClosed` fire at all — without the
  reply OkHttp waits the socket out instead.
- `connect()` breaks the retry loop on `revoked` instead of backing off.
- `AppViewModel.onRevoked()` tears the live channel down first (otherwise its collectors keep running
  against a socket that will never return), then clears the token and raises `PAIR_NEEDED` — the **same**
  recovery the HTTP-401 path already does, because it is the same fact arriving over the other transport.
- A separate `revoked` UI flag, kept apart from `disconnected` on purpose: the two need opposite messages.
  "Reconnecting…" is a promise the app cannot keep once the token is dead.

## Verified on an emulator — all three form factors

| | revoked while connected | ordinary drop |
|---|---|---|
| **Phone** (1080×2340) | banner *"Access revoked — pair again to reconnect."* + pairing dialog, immediately | — |
| **Tab S8** (2560×1600, landscape two-pane) | same, above both panes | — |
| **Bigme B7** (1264×1680, **Color E-Ink profile ON**) | same, mono/high-contrast, no hue | — |

The regression that actually mattered, on the phone: stopping the bridge still shows **"Connection lost —
reconnecting…"** with *no* pairing dialog, and starting it again reconnects silently — same device id
`dv_K0UbM-5X`, token intact. The two paths are now distinct in both directions, which is the whole point;
a fix that made every disconnect drop the token would have been worse than the bug.

Each cycle was a real end-to-end run: pair with a code minted by `gitview-bridgectl pair`, browse to open
the live channel, confirm `devices` shows `CONNECTED yes`, then revoke from the host.

## Not done

No unit test. The behaviour lives in an OkHttp `WebSocketListener` and the retry loop, so covering it
needs a local WS server that can close with a chosen code — worth doing, not done here. Emulator runs on
all three form factors are the evidence for now, and they were driven by hand rather than scripted.

Also observed, unrelated and unfiled: after killing an emulator abruptly the bridge kept reporting that
device as `CONNECTED yes` for several minutes — the socket dies with the VM and nothing tells the bridge.
Ordinary TCP behaviour, and a ping/idle reaper would tighten it, but worth knowing before trusting the
column to be instantaneous.

## Folded into the ADR-037 change

Originally a standalone branch off `main`. Moved into the legacy-auth removal once the dependency became
clear: de-authorising a device is exactly what closes its socket with `4401`, so ADR-037 without this fix
would drop **all 6 quartz devices into the permanent reconnect loop at once** — the bug's worst case,
triggered deliberately. Shipping them apart was never safe. The PLAN entry is marked done there.
